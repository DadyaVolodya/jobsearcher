# Механика тестирования

## Проблема

Единый набор заданий быстро расходится между кандидатами. Генерация «с нуля» нейросетью плохо сопоставима по сложности.

## Решение MVP

1. **Банк параметризованных заданий** (`test_item`) с вариантами формулировок (`variants_json`) и пулом опций.
2. **Уникальная сессия**: `seed = CRC32(candidateId + attemptId)`.
3. На seed: shuffle заданий, выбор variant, shuffle options.
4. Кандидату отдаются только `code/label` опций без флага correct.
5. Оценка MCQ — по эталону; OPEN_TEXT — по rubric keywords.
6. IT: банк по специализациям (Backend, Frontend, QA, DevOps, Data, Mobile) и грейдам; другие отрасли — короткий MCQ.
7. Перед стартом теста обязательна завершённая отраслевая анкета (или непустой `survey_vector` у демо-профилей).

## Грейд (по ТЗ)

- Порог подтверждения: overall ≥ 0.6 и junior-floor ≥ 0.5.
- При провале целевой грейд **не подтверждается**, но уже назначенный грейд **не понижается автоматически**.
- В ответе сессии возвращается `suggestedRetryGrade` — предложение пересдать на более низкий/доступный грейд.
- Провал прокторинга (`LEFT_WINDOW`): попытка засчитана как fail, грейд не сбрасывается в JUNIOR.
- Смена / пересдача: не чаще 1 раза в **30** дней (`GradeChangePolicy`).

## Устойчивость к leak

Даже при публикации ответов «варианта A» другой кандидат получает другой seed/порядок/формулировку. Сопоставимость сохраняется за счёт общего банка и единых эталонов.
